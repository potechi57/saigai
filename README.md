島根県の道路防災カルテ点検業務をWeb GIS化するプロジェクト。設計の背景は
[../12_DATA_MODEL_WEBGIS_MVP.md](../12_DATA_MODEL_WEBGIS_MVP.md) を参照。

### 様式Ｂ・様式Ｃ・様式Ｄの再現について

紙の様式は「詳細スケッチ欄」「写真張付欄」等が固定2枠だが、Web版では点検対象・カルテ
それぞれに複数枚の写真をアップロードできるようにしている（デジタル化のメリットとして
柔軟性を優先し、忠実な再現よりも実用性を取った数少ない箇所）。それ以外の項目配置・
labelの文言は実際の様式にできるだけ合わせている。

指示書22章のフェーズ分割に沿って、次はPhase 5「スマートフォン向け現場UI」に進む想定。

### Excel取込について

防災カルテ様式（全国地質調査業協会連合会 平成25年7月版）のExcelファイルをアップロードすると、
様式Ａ（基本情報）・様式Ｃ（点検履歴）の内容を読み取ってカルテを登録・更新する
（`lib/excel/karte-import.ts`・`lib/actions/import-actions.ts`）。

- **暗号化への対応**: 同様式の一部は`VelvetSweatshop`という固定パスワードで保護されている
  （実質的なセキュリティ機能ではなく、Excelが一部の保護付きテンプレートに一律で使う
  周知のデフォルト値）。`officecrypto-tool`で復号し、`xlsx`（SheetJS）で解析する。
  どちらもNode.js単体で完結し、Pythonなどの追加ランタイムは不要（実ファイルで検証済み）。
- **`xlsx`はnpm公式レジストリではなくSheetJS公式CDN経由でインストールしている**
  （npm版には未修正の脆弱性が2件あるため。`package.json`の依存関係を参照）。
- **セル位置ではなく色だけでは判定できない**ことを実データで確認した（同じ「データが
  入っているセル」でも、路線名は緑、点検対象項目は白だった）。そのため色ではなく、
  様式の固定されたセル位置を主な抽出方法にしている。
- **取込対象フィールド**（様式Ａ）: 施設管理番号・カルテ区分・管理機関名／コード・
  台帳番号・路線名・距離標（自／至）・上下線の別・延長・事業区分・道路種別・
  現道旧道区分・所在地（都道府県〜大字等）・位置目印・緯度経度・測地系・
  事前通行規制区間指定・交通量（平日または休日）・ＤＩＤ区間・バス路線・迂回路・
  緊急輸送道路区分。いずれも島根県の実データ複数件（`B1432A279`・`B1432A020`・
  `B3101A019`）で値セルの位置を確認済み。
- **現時点の制限**（実データの記入例が無く未対応、またはあえて対象外にしたもの）:
  - 様式Ｂ（点検対象の名称）は未対応。取込時は「点検対象1（Excel取込・要確認）」という
    プレースホルダを自動作成するので、取込後に編集画面から実際の名称に直す想定。
  - 着目すべき変状が複数ある場合の使い分け、8回以上の点検履歴（シート複製）、
    様式Ｄ（災害履歴）は未対応。
  - 規制基準等（連続雨量・時間雨量）は、ラベル・単位セルの位置は確認できたが、
    実データ3件とも値が未記入だったため値セルの位置が確認できておらず対象外。
  - 交通量は様式上「平日／休日」いずれか1種別しか記入欄が無いらしく
    （実データ3件は全て「平日」）、種別セルの表記を見てKarte.trafficVolumeWeekday／
    trafficVolumeHolidayのどちらに入れるか決めている（両方の値を同時に取り込むことは
    想定していない）。
- **再取込の扱い**: 施設管理番号が同じカルテへの再アップロードは上書き更新になる。
  点検記録はカルテ×点検日の組で一意にしているため、同じファイルを再取込しても
  点検記録が重複作成されることはない。
- **施設管理番号が空の場合**: ファイル名から仮の番号（例:`IMPORT-<ファイル名>-<タイムスタンプ>`）
  を自動生成する。実データでの検証時、テストファイルの施設管理番号欄が実際に空だった
  ことを確認済み。
- **大きいファイルのアップロード**: 実際の防災カルテExcelは様式Ｂ・Ｃに写真が埋め込まれて
  おり、数MB〜10MB近くになることが多い。Next.jsのServer Actionは既定で本文1MBまでという
  上限があり、さらに本番（Vercel）ではVercel Functions自体のリクエストサイズ上限が別途ある
  （`next.config.mjs`の`bodySizeLimit`緩和だけでは本番では不十分）。そのため、
  一定サイズ（700KB）を超えるファイルはブラウザから直接Vercel Blobへアップロードし、
  Server ActionにはそのURLだけを渡す方式にしている（`app/api/blob-upload/route.ts`が
  クライアントアップロード用トークンの発行だけを担い、実体はブラウザ→Blobへ直接PUTされる）。
  ローカル開発などVercel Blob未設定の環境では、この直接アップロードが失敗した場合に
  従来どおりファイル本体を直接Server Actionに送る経路へ自動的にフォールバックする
  （`components/ExcelImportForm.tsx`参照）。
- **セル位置は必ず記入済みの実データで検証する**: 初版は施設管理番号などが未入力の
  テストファイル1件のみで検証しており、施設管理番号（実際は9マス。8マスと誤認していた）・
  点検対象項目（カルテ区分）・路線名・距離標（自）／（至）の列位置に誤りがあった。
  空のセルは列がずれていても単に空文字列を返すだけで気づけないため、この種のバグは
  記入済みの実データで実際に値を突き合わせないと発見できない。島根県の実データ複数件
  （`B1432A279`・`B1432A020`・`B3101A019`）で再検証し修正済み。

### 写真アップロードについて

点検対象ごとに画像をアップロードできる（`lib/actions/photo-actions.ts`）。データ本体は
Excel取込、写真は別アップロードという指示に沿い、独立した仕組みにしている。

- 保存先はVercel Blob。ローカル開発では`.env`に`BLOB_READ_WRITE_TOKEN`が必要
  （`.env.example`参照）。本番（Vercel）では、Vercelダッシュボードで**Blobストアを
  作成しこのプロジェクトに接続する**だけでよい。接続方式には2通りあることを実データで
  確認済み: (1) 従来の固定トークンが`BLOB_READ_WRITE_TOKEN`として自動設定される、
  (2) 新しいOIDC方式では`BLOB_READ_WRITE_TOKEN`は設定されず`VERCEL_OIDC_TOKEN`のみが
  設定される（Vercel側が「All connected projects use OIDC」と案内するプロジェクトで
  実際にこちらだった）。どちらの方式でも動くよう、認証情報の有無チェックは
  `BLOB_READ_WRITE_TOKEN`と`VERCEL_OIDC_TOKEN`のいずれかが存在すればOKと判定している
  （`lib/actions/photo-actions.ts`の`hasBlobCredentials()`）。
- **実装中に発見した問題**: `@vercel/blob`は認証情報が全く無い場合、即座には失敗せず
  内部のリトライ処理で1分以上待たされた末にエラーになることを実際に確認した。
  UXが悪いため、呼び出し前に認証情報の有無を自前でチェックし、
  未設定なら即座に分かりやすいエラーを返すようにしている（Excel取込側の原本保存も同様）。
  この修正はNode.jsから関数を直接呼び出すテストで1ミリ秒で正しくエラーになることを確認済み。
- Vercel Blobの実トークンでの実アップロード（実際に画像が保存されること）は、
  今回はトークン未設定のため未検証。設定後に確認が必要。

### 編集画面の設計メモ

- フォームはすべてServer Actions（`lib/actions/karte-actions.ts`）で実装しており、
  JavaScript無効でも動作するプログレッシブエンハンスメント（`<form action={serverAction}>`）。
  そのため`fetch`ベースのAPIルートは作っていない。
- 削除は指示書12章の方針通り、点検対象の削除を論理削除（`isActive`フラグ）＋
  クライアント側の確認ダイアログ（`components/ConfirmSubmitButton.tsx`）の両方にしている。
  カルテ自体・点検記録の削除機能はまだ未実装（今のところ作りすぎないよう見送っている）。
- zod等のバリデーションライブラリは導入せず、`lib/actions/karte-actions.ts`内の
  簡単な手作業パースにとどめている（アプリを不必要に大きくしない方針）。

### 地図ライブラリについて

指示書はGoogle Maps Platformを想定していたが、APIキーが未取得のため、MVPでは
APIキー不要のLeaflet + OpenStreetMapタイルを採用した（指示書3章「地図表示部分と業務データを
疎結合にする」方針の通り、地図の実装は`components/MapView.tsx`に閉じ込めてあるため、
Google Maps Platform等への差し替えはこのファイルの中身を変更するだけで済む）。

## スタック

Next.js（App Router）+ TypeScript + TailwindCSS + Prisma + PostgreSQL。Vercelへのデプロイを想定。

## セットアップ

### 1. 依存関係のインストール

```bash
npm install
```

### 2. データベースの用意

Vercel Postgres（Neon）を使うのが最も簡単（Vercelダッシュボード → Storage → Create Database → Postgres）。
ローカルのみで試す場合は Neon の無料枠を別途作成するか、Docker で代用できる。

```bash
docker run --name karte-db -e POSTGRES_PASSWORD=postgres -p 5432:5432 -d postgres:16
```

`.env.example` を `.env` にコピーし、`DATABASE_URL` を接続文字列に置き換える。

### 3. マイグレーションとサンプルデータ投入

```bash
npm run prisma:migrate   # テーブルを作成
npm run db:seed          # サンプルカルテ（架空データ）を投入
```

### 4. 開発サーバー起動

```bash
npm run dev
```

`http://localhost:3000` にアクセスするとカルテ一覧へリダイレクトされる。

## Vercelへのデプロイ

1. このリポジトリ（`webgis-mvp/`をルートとして）をVercelにインポート
2. Vercelダッシュボードで Postgres（Neon）を作成し、プロジェクトに接続すると
   `DATABASE_URL` が自動的に環境変数として設定される
3. デプロイ後、初回のみ `npx prisma migrate deploy` を実行してテーブルを作成する
   （Vercelのビルドコマンドに含めるか、ローカルから本番の`DATABASE_URL`に向けて実行する）
