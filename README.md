### 地図中心のカルテ検索画面について

`/karte`は元々「検索フォーム＋『一覧』『地図』タブ」という構成だったが、
「地図を中心とした画面にしてほしい。初期表示は地図だけで、カルテ一覧などは
表示しない」という要望を受けて、次のレイアウトに刷新した。

- ヘッダー（`h-14`固定）の直下から画面下端まで（`h-[calc(100vh-3.5rem)]`）を
  隙間なく使い、左に検索条件パネル（幅固定`w-80`〜`w-96`）、残り全体に地図を
  常時表示する。他ページのような`mx-auto max-w-*`や`<main>`のpaddingは
  このページだけ意図的に持たせていない（`app/layout.tsx`が`<main>`に一律の
  paddingを付けるのをやめ、他の各ページが自分のトップレベル要素に`p-6`を
  指定する形に変更した。理由はコメント参照）。
- 初期表示（検索条件が1つも無い状態）では、カルテの一覧テーブルは一切出さず、
  地図に現在登録されている全カルテのピンだけを表示する。詳細情報は常時出さず、
  ピンをクリック（＝その地点を選択）した時のポップアップに追い出すことで、
  地図上の情報量を最小限にとどめている（凡例・現在地/ホーム位置ボタンも、
  地図の上に浮かせるオーバーレイに変更し、地図自体が親要素いっぱいを
  占められるようにした。`components/MapView.tsx`）。
- 「一覧」表示に切り替えられる唯一の入り口は、検索条件パネル内の
  「検索結果を一覧で表示する」ボタン。チェックボックスではなく、検索ボタンと
  同じ`<form>`内の別の送信ボタン（`name="view"`の値だけが異なる）として実装しており、
  JS無しでもその場の検索条件のまま切り替わる。検索ボタン自身も現在の`view`を
  保持したまま送信するため、一覧表示中に条件を変えて検索し直しても地図表示に
  戻ってしまわない。検索条件と表示方法（地図/一覧）を両方ともcrawlable/共有可能な
  クエリパラメータにしている。
- 検索条件パネルの下部に「最近の検索」を表示する（`components/SearchHistoryPanel.tsx`）。
  ログイン機能が無いMVPのため、事務所で共有するのではなく端末（ブラウザ）ごとの
  localStorageに保持する。表示方法（`view`）は検索条件ではないため、記録対象からは
  除外している。
- ヘッダーには`relative z-[2000]`を指定している。地図（`components/MapView.tsx`）の
  凡例・ボタン類オーバーレイは`z-[1000]`だが、ヘッダー自体がスタッキングコンテキストを
  作っていないと、ヘッダー内の要素（閲覧履歴ドロップダウン等）にどれだけ大きい
  z-indexを与えても地図側の`z-[1000]`に勝てず、ドロップダウンが地図の裏に隠れてしまう
  （実際に発生した不具合）。ヘッダー自身に地図より大きいz-indexを与えることで解消した。
- 地図上部中央に「場所を検索（例: ○○小学校）」ボックスがある。カルテの属性検索
  （左の検索条件パネル）とは別物で、地名・施設名から地図を移動するためのジオコーディング
  検索（Nominatim、APIキー不要）。詳細は下記「場所検索（ジオコーディング）について」参照。

### 様式Ｂ・様式Ｃ・様式Ｄの再現について

様式Ｂ（カルテ詳細画面の様式Ｂタブ・点検対象編集画面の両方）は、実データ複数件で
写真の埋め込み位置（drawingのアンカー座標）まで確認した上でレイアウトを組んでいる。
実際の様式は左に<詳細スケッチ欄>（写真2枚を縦に並べる）、右に<写真張付欄>
（大きめの写真1枚）とその下に「着目すべき点」「チェック項目」という左右2列構成
だった。実データでは<詳細スケッチ欄>にも手描きスケッチではなく実際の写真が貼られて
いたため、Web版でも3枠とも写真として扱う（先頭3枚を上記の配置に当てはめ、4枚目
以降は末尾にまとめて表示。複数枚アップロードできるというWeb版の柔軟性は残している）。
空の枠は「写真なし」と明示する。この写真枠は`components/PhotoSlot.tsx`として共通化し、
カルテ詳細画面（閲覧のみ・点検対象ごとに縦に並べる）と点検対象編集画面（フォーム
入力込み）の両方から使っている。
様式Ｂは実際のExcelでも点検対象（変状）ごとにシートが分かれるため、Web版でも
様式Ａ・様式Ｃと同様にカルテ詳細画面の独立したタブとして実装している。
点検対象が複数ある場合は、様式Ａ／様式Ｂ／様式Ｃ／様式Ｄを切り替える`SheetTabs`を
様式Ｂタブの中にもう一段入れ子にして、対象ごとに①②③…のタブで切り替える
（最初は対象を縦に並べて全部同時に表示していたが、対象数が増えるほど様式Ｂの
表示全体が縦に間延びしてしまっていたため、様式Ａ／Ｂ／Ｃと同じタブ切り替え方式に
統一した）。様式Ｄ（後述）も同じ理由・同じ方式で、災害履歴が複数件ある場合に
入れ子タブにしている。

`PhotoSlot`の`fit`プロパティで、写真のトリミング方針を2通り使い分けている。既定の
`fit="cover"`は指定した高さの枠いっぱいに敷き詰める代わりに縦横比が合わない部分が
切れる（<写真張付欄>のように1枚を大きく見せたい用途向け）。<詳細スケッチ欄>の
2枚は逆に「一部が切れて見えなくなる」ことを避けたかったため`fit="contain"`にし、
高さは固定したまま（＝写真が何枚・どんな縦横比でも様式Ｂ全体の高さは常に一定）
トリミング無しでレターボックス表示にしている。当初は高さも写真の縦横比に
合わせる`h-auto`案を試したが、縦長の写真1枚で様式Ｂ全体が非常に大きくなって
しまう問題が実際に起きたため、高さ固定＋`object-contain`の組み合わせに落ち着いた
（`components/PhotoSlot.tsx`のコメント参照）。

様式Ｃのテーブルには、以前の設計の名残で点検対象ごとに「写真」行（サムネイル＋
アップロードフォーム）が残っていたが、写真の追加・確認は様式Ｂタブで完結するため
撤去した。また、既定のtable layout（auto）だと「点検時の特記事項」等、文章量の
多いセルに列幅が引っ張られ、点検日ごとの列幅がばらばらになる問題があったため、
`table-fixed`＋各列への明示的な幅指定に変更し、はみ出す文章は横に伸ばさず
縦に折り返すようにしている。

様式Ｄ（災害履歴）は当初、実際のExcelを精査せず一般的な項目を並べただけの表に
なっていたが、実データ（08_B1432A020等）でセル配置を確認した上で作り直した。
実際の様式は上段が様式Ａと同じカルテ共通情報の再掲（施設管理番号・路線名・
台帳番号・距離標・事業区分・道路種別・所在地・緯度経度・測地系）＋「点検対象箇所」
（どの点検対象の変状で発生した災害かを示す。`DisasterEvent.targetId`に対応）、
中段が左に<平面図（被災・対策）><現況写真・スケッチ（被災・対策）>の2枠、右に
<断面図（被災・対策）>1枠とその下の特記事項（発生年月日・規模・誘因・被害・
通行止実績・対策工、各コメント欄付き）、下段が様式Ａ・様式Ｂと同じ作成年月日／天候、
という構成だった。データモデル（`DisasterEvent`）は元々この構成を見越して各項目を
持っていたため、スキーマ変更は不要だった。
3枚の画像は様式Ｂと同じ「先頭N枚を固定配置に当てはめる」方式にしているが、
様式Ｂと異なりdrawingのアンカー位置までは確認していないため、平面図→断面図→
現況写真・スケッチという割当順は様式の並び順からの推測（要検証、
`app/karte/[karteNo]/page.tsx`のコメント参照）。なお、様式Ｄからの手動登録・
写真アップロード用の編集画面はまだ無く（様式Ａ〜Ｃと異なり作成・編集フォーム未実装）、
現時点では閲覧専用（既存データの表示）にとどまる。

点検地点位置図・現況写真（様式Ａ）は基本的に1〜2枚程度を想定し、大きめのサムネイル
（`h-[28rem] w-[28rem]`、約448px）で見やすく表示する。未登録の場合は「写真なし」と
明示する（枠だけ表示されて空欄なのか未実装なのか分からない状態を避けるため）。

### ページ幅について

ページごとに最大幅を決めている（`app/layout.tsx`の`<main>`自体は幅を制限せず、
各ページのトップレベル要素が`mx-auto max-w-*`を指定する）。検索・一覧や各種フォームは
表示要素が少ないため`max-w-5xl`のまま、様式Ａ・様式Ｃ等の横に広い表を持つカルテ詳細
画面だけ`max-w-[1800px]`と広めにしている。全ページ一律に広げると、要素の少ない画面まで
間延びしてしまうため（実際に検索・一覧画面を広げすぎて地図タブが縦スクロール必須に
なった失敗を踏まえての方針）。

指示書22章のフェーズ分割に沿って、次はPhase 5「スマートフォン向け現場UI」に進む想定。

### Excel取込について

防災カルテ様式（全国地質調査業協会連合会 平成25年7月版）のExcelファイルをアップロードすると、
様式Ａ（基本情報）・様式Ｃ（点検履歴）の内容を読み取ってカルテを登録・更新する
（`lib/excel/karte-import.ts`・`lib/actions/import-actions.ts`）。

- **暗号化への対応**: 同様式の一部は`VelvetSweatshop`という固定パスワードで保護されている
  （実質的なセキュリティ機能ではなく、Excelが一部の保護付きテンプレートに一律で使う
  周知のデフォルト値）。`officecrypto-tool`で復号し、`xlsx`（SheetJS）で解析する。
  どちらもNode.js単体で完結し、Pythonなどの追加ランタイムは不要（実ファイルで検証済み）。
- **`xlsx`はnpm公式レジストリではなくSheetJS公式CDN経由でインストールしている**
  （npm版には未修正の脆弱性が2件あるため。`package.json`の依存関係を参照）。
- **セル位置ではなく色だけでは判定できない**ことを実データで確認した（同じ「データが
  入っているセル」でも、路線名は緑、点検対象項目は白だった）。そのため色ではなく、
  様式の固定されたセル位置を主な抽出方法にしている。
- **取込対象フィールド**（様式Ａ）: 施設管理番号・カルテ区分・管理機関名／コード・
  台帳番号・路線名・距離標（自／至）・上下線の別・延長・事業区分・道路種別・
  現道旧道区分・所在地（都道府県〜大字等）・位置目印・緯度経度・測地系・
  事前通行規制区間指定・交通量（平日または休日）・ＤＩＤ区間・バス路線・迂回路・
  緊急輸送道路区分・専門技術者による点検・着目すべき変状・点検内容の要点・
  専門技術者のコメント・対応区分／評価年月日（4択のうち"○"が付いている行を判定）・
  点検の時期／頻度・想定される災害形態・変状が出たときの対応・主な災害形態
  （落石／崩壊。KarteRockfallDetailも作成・更新）・点検者名／会社名／連絡先・
  専門技術者名／会社名／連絡先・作成年月日・天候。いずれも島根県の実データ複数件
  （`B1432A279`・`B1432A020`・`B3101A019`）で値セルの位置を確認済み。
- **様式Ｂ（変状/点検対象ごとの詳細記録）の取込**（`findFormBSheetNames`・
  `extractFormBTarget`）: 様式Ｂのシート名は変状が1件だけなら"様式Ｂ"、複数あれば
  "様式Ｂ (1)"「様式Ｂ(2)"のように連番が付く（実データで確認済み。括弧前の半角
  スペース有無が統一されていないため両方にマッチする正規表現にしている）。シートごとに
  点検対象を1件作成・更新し、着目すべき点・チェック項目・作成年月日・天候を取り込む。
  変状No.（①②…の丸数字）をInspectionTarget.sequenceNoに変換して使うため、
  様式Ｃの点検履歴（後述）と正しく紐付く。対象の名称は様式Ｂに記入欄が無いため、
  引き続き「点検対象N（Excel取込・要確認）」という仮の名称にしている
  （取込後に編集画面から直す想定。既存の名称は上書きしない）。
  - 様式Ｃには、対応する様式Ｂのシートが無くなった変状（過去に追跡していたが
    現在は様式Ｂページ自体が削除されている等）の履歴が残っていることを実データで
    確認したため、様式Ｃの処理側で様式Ｂに無いsequenceNoを見つけた場合も、
    履歴を取りこぼさないよう追加でプレースホルダの点検対象を作成する。
- **現時点の制限**（実データの記入例が無く未対応、またはあえて対象外にしたもの）:
  - 8回以上の点検履歴（シート複製）、様式Ｄ（災害履歴）は未対応。
  - 規制基準等（連続雨量・時間雨量）は、ラベル・単位セルの位置は確認できたが、
    実データ3件とも値が未記入だったため値セルの位置が確認できておらず対象外。
  - 交通量は様式上「平日／休日」いずれか1種別しか記入欄が無いらしく
    （実データ3件は全て「平日」）、種別セルの表記を見てKarte.trafficVolumeWeekday／
    trafficVolumeHolidayのどちらに入れるか決めている（両方の値を同時に取り込むことは
    想定していない）。
  - 「着目すべき変状」は様式内に2箇所（①専門技術者による点検欄の下の一言、②点検の時期等と
    並ぶ表の中）あり、実データでは内容が異なっていた。Karte.keyDeformationSummaryは
    1カラムしか無いため①（点検内容の要点と対になっている方）のみを取り込んでいる。
  - 点検の時期は「①定期・(頻度)」「②不定期・豪雨」「③不定期・震度」の3行があるが、
    ②③は実データ3件とも固定的な参考文言（フォームの既定注記）だったため①のみを取り込み、
    常にinspectionPeriodType=REGULARとしている（不定期側が選択されている実データが
    無く、判定方法が未確認のため）。
  - 様式Ｃの「点検後の対応（専門技術者の判定）」は、実データ3件とも未記入だったため
    値セルの位置を確認できていない。直前の「点検者名」項目（ラベルと同じ行に値が入る）
    と同じ並びだろうという推測でセル位置を実装しているが未検証（記入例が見つかり次第
    要確認。誤っていても実害は無記入がnullのままになるだけ）。
- **様式Ｃの取込対象フィールド**: 点検年月日・点検者名・天候・変状（点検対象）ごとの
  状況コメント・前回との差異・被災履歴・補修履歴・点検時の特記事項・専門技術者による
  点検年月日・専門技術者名・点検後の対応（専門技術者の判定。上記の通り未検証）・
  次回点検実施時期。変状ごとの結果（状況コメント・前回との差異・被災履歴・補修履歴）は
  縦方向に最大4件まで、1件あたり5行を占める配置（実データで確認済み: 1件目は行6〜10、
  2件目は行11〜15、以降5行おき）になっており、各行の変状No.（①②…）から
  InspectionTarget.sequenceNoを特定してInspectionResultを紐付ける。
- **埋め込み画像の自動取込**（`lib/excel/karte-image-extract.ts`の`extractSheetImages`）:
  様式Ａ・様式Ｂシートに埋め込まれた画像を、それぞれカルテ本体・対応する点検対象の
  写真として自動登録する。
  - `.xlsx`の実体はZIPであることを利用し、`xlsx`パッケージが内部で使う`CFB`モジュール
    （本来はOLE複合文書用だが同じインターフェースでZIPも読める）で生バッファから直接
    `xl/drawings`・`xl/media`を辿って画像バイナリを取り出している。新規の依存ライブラリは
    追加していない。`XLSX.read()`で得られる通常のWorkBookは埋め込み画像を保持しないため、
    別途この方法が必要だった。
  - 対象は指定シートのdrawingにひもづくJPEG/PNG/GIF/BMP/WEBPのみ。実データで、様式Ａの
    「点検地点位置図」にスケッチ画像がEMF（ベクター形式、ブラウザで直接表示できない）で
    埋め込まれていることを確認したため、これは対象外にしている（変換には別途重い
    ライブラリが必要）。
  - 様式Ｂは実データで<詳細スケッチ欄>に2枚・<写真張付欄>に1枚（計3枚）という配置を
    複数件で確認済み。画像の貼り付け位置（アンカーのセル座標）を列→行の順にソートすると
    自然に「左上→左下→右」の順になるため、点検対象編集画面の3枠（詳細スケッチ欄2枠＋
    写真張付欄1枠）にそのまま対応させている。
  - 「R7現状記録写真」等ほかのシートの画像は今のところ対象外。
  - 再取込のたびに写真が重複して増えないよう、前回のExcel由来の写真
    （`sourceForm=FORM_A`／`FORM_B`）は入れ替える。手動アップロード分
    （`sourceForm=OTHER`）は対象外なので消えない。
  - Vercel Blob未設定の環境（ローカル開発等）では取込全体には影響させず、写真取込だけを
    ベストエフォートでスキップする。
- **再取込の扱い**: 施設管理番号が同じカルテへの再アップロードは上書き更新になる。
  点検記録はカルテ×点検日の組で一意にしているため、同じファイルを再取込しても
  点検記録が重複作成されることはない。
- **施設管理番号が空の場合**: ファイル名から仮の番号（例:`IMPORT-<ファイル名>-<タイムスタンプ>`）
  を自動生成する。実データでの検証時、テストファイルの施設管理番号欄が実際に空だった
  ことを確認済み。
- **大きいファイルのアップロード**: 実際の防災カルテExcelは様式Ｂ・Ｃに写真が埋め込まれて
  おり、数MB〜10MB近くになることが多い。Next.jsのServer Actionは既定で本文1MBまでという
  上限があり、さらに本番（Vercel）ではVercel Functions自体のリクエストサイズ上限が別途ある
  （`next.config.mjs`の`bodySizeLimit`緩和だけでは本番では不十分）。そのため、
  一定サイズ（700KB）を超えるファイルはブラウザから直接Vercel Blobへアップロードし、
  Server ActionにはそのURLだけを渡す方式にしている（`app/api/blob-upload/route.ts`が
  クライアントアップロード用トークンの発行だけを担い、実体はブラウザ→Blobへ直接PUTされる）。
  ローカル開発などVercel Blob未設定の環境では、この直接アップロードが失敗した場合に
  従来どおりファイル本体を直接Server Actionに送る経路へ自動的にフォールバックする
  （`components/ExcelImportForm.tsx`参照）。
- **取込作業の進捗表示**: 「①ブラウザ→Blobへのアップロード」は`@vercel/blob/client`の
  `onUploadProgress`で実際のバイト単位%を表示する。その後のサーバー側処理は、
  「①アップロード100%＝実際にカルテが見られるようになる」と誤解されるほどの時間差が
  あった（写真のアップロード・点検対象ごとの処理等、実際にはこの間に多くの作業が
  行われているが、それを示す手段が無かったとのフィードバックを受けた）ため、
  単一のServer Action呼び出しではなく、複数回に分割した呼び出しに変更した
  （`importPhase1KarteAndFormA`→`importPhase2FormBTarget`×様式Ｂのシート数→
  `importPhase3Events`の順、`lib/actions/import-actions.ts`）。各フェーズはBlob上の
  ファイルを毎回取得し直す（Server Actionはリクエストごとに独立しており、前の呼び出しで
  パース済みのWorkBookをメモリ上に持ち越せないため）。呼び出し元
  （`components/ExcelImportForm.tsx`）は1回の呼び出しが完了するたびに
  「②点検対象を取込中（1/3）」のように実際の完了数/全体数で進捗を進めるため、
  100%になるタイミングと最終フェーズ（`importPhase3Events`。ここで初めて
  `revalidatePath`する）が完了する＝実際にカルテが見られるようになるタイミングが一致する。
  小さいファイル（Blob未設定のローカル開発等）は、従来どおり1回のServer Action呼び出し
  （`importKarteExcel`）で処理し、進捗は不確定スピナーのみ表示する。
- **セル位置は必ず記入済みの実データで検証する**: 初版は施設管理番号などが未入力の
  テストファイル1件のみで検証しており、施設管理番号（実際は9マス。8マスと誤認していた）・
  点検対象項目（カルテ区分）・路線名・距離標（自）／（至）の列位置に誤りがあった。
  空のセルは列がずれていても単に空文字列を返すだけで気づけないため、この種のバグは
  記入済みの実データで実際に値を突き合わせないと発見できない。島根県の実データ複数件
  （`B1432A279`・`B1432A020`・`B3101A019`）で再検証し修正済み。

### 写真アップロードについて

点検対象ごとに画像をアップロードできる（`lib/actions/photo-actions.ts`）。データ本体は
Excel取込、写真は別アップロードという指示に沿い、独立した仕組みにしている。

- 保存先はVercel Blob。ローカル開発では`.env`に`BLOB_READ_WRITE_TOKEN`が必要
  （`.env.example`参照）。本番（Vercel）では、Vercelダッシュボードで**Blobストアを
  作成しこのプロジェクトに接続する**だけでよい。接続方式には2通りあることを実データで
  確認済み: (1) 従来の固定トークンが`BLOB_READ_WRITE_TOKEN`として自動設定される、
  (2) 新しいOIDC方式では`BLOB_READ_WRITE_TOKEN`は設定されず`VERCEL_OIDC_TOKEN`のみが
  設定される（Vercel側が「All connected projects use OIDC」と案内するプロジェクトで
  実際にこちらだった）。どちらの方式でも動くよう、認証情報の有無チェックは
  `BLOB_READ_WRITE_TOKEN`と`VERCEL_OIDC_TOKEN`のいずれかが存在すればOKと判定している
  （`lib/actions/photo-actions.ts`の`hasBlobCredentials()`）。
- **実装中に発見した問題**: `@vercel/blob`は認証情報が全く無い場合、即座には失敗せず
  内部のリトライ処理で1分以上待たされた末にエラーになることを実際に確認した。
  UXが悪いため、呼び出し前に認証情報の有無を自前でチェックし、
  未設定なら即座に分かりやすいエラーを返すようにしている（Excel取込側の原本保存も同様）。
  この修正はNode.jsから関数を直接呼び出すテストで1ミリ秒で正しくエラーになることを確認済み。
- Vercel Blobの実トークンでの実アップロード（実際に画像が保存されること）は、
  今回はトークン未設定のため未検証。設定後に確認が必要。

### 編集画面の設計メモ

- フォームはすべてServer Actions（`lib/actions/karte-actions.ts`）で実装しており、
  JavaScript無効でも動作するプログレッシブエンハンスメント（`<form action={serverAction}>`）。
  そのため`fetch`ベースのAPIルートは作っていない。
- 削除は指示書12章の方針通り、点検対象の削除を論理削除（`isActive`フラグ）＋
  クライアント側の確認ダイアログ（`components/ConfirmSubmitButton.tsx`）の両方にしている。
  カルテ自体・点検記録の削除機能はまだ未実装（今のところ作りすぎないよう見送っている）。
- zod等のバリデーションライブラリは導入せず、`lib/actions/karte-actions.ts`内の
  簡単な手作業パースにとどめている（アプリを不必要に大きくしない方針）。

### 地図ライブラリについて

指示書はGoogle Maps Platformを想定していたが、APIキーが未取得のため、MVPでは
APIキー不要のLeaflet + OpenStreetMapタイルを採用した（指示書3章「地図表示部分と業務データを
疎結合にする」方針の通り、地図の実装は`components/MapView.tsx`に閉じ込めてあるため、
Google Maps Platform等への差し替えはこのファイルの中身を変更するだけで済む）。

### ホーム位置と距離表示について

県土整備事務所等、点検の起点となる拠点を「ホーム位置」として地図上から設定できる
（`/karte`地図右上の「🏠 ホーム位置を設定」→地図をクリック）。ログイン機能が無い
MVPのため、ユーザーごとではなく事務所で1つを共有するシングルトン設定
（`AppSettings`テーブル、`lib/actions/settings-actions.ts`）として保存する。

マーカー（カルテ地点）をクリックして選択すると、ポップアップ内に以下を表示する
（`components/MapView.tsx`）:

- **ホームからの直線距離**・**現在地からの直線距離**（Haversine公式、`lib/geo.ts`）。
  常時全マーカーぶん計算すると地図上の情報量が増えすぎるため、ポップアップを
  開いた＝その地点を選択した瞬間にだけ計算する。現在地は「📍 現在地」ボタンで
  取得済みの場合のみ表示する。
- **道路距離（試験的）**: ポップアップ内のボタンを押すとオンデマンドで取得する。
  実装にはOSRM（Open Source Routing Machine）の公開デモサーバーを使っている
  （APIキー不要で唯一気軽に試せる選択肢だが、あくまで動作確認用の共用サーバーで
  SLAが無く商用の常用には向かない）。そのため既定では呼ばず、ボタンを押した
  ときだけ1回叩く形にしている。本格運用する場合は自前でOSRMを立てるか、
  Google Directions等の有償APIへの切り替えが必要（`lib/geo.ts`冒頭のコメントも参照）。
- **☆/★お気に入りボタン**: そのカルテをその場でお気に入りに追加/解除できる
  （下記「お気に入り機能について」参照）。ポップアップの中身はマーカー作成時に
  1度だけ生成した固定文字列のため、切り替え後の状態（★の重ね表示含む）は
  `favoriteIdsRef`というrefで保持し、ポップアップを開き直すたびに反映し直す
  （ホーム/現在地からの距離と同じ仕組み。`home`が変わっても地図全体を作り直さない
  設計に合わせている）。

### 場所検索（ジオコーディング）について

地図上部中央の検索ボックスは、カルテの属性検索とは別に「○○小学校のような場所を
探して地図を移動したい」という要望に応えるためのもの。ジオコーディング（地名→
緯度経度の変換）にはNominatim（OpenStreetMapの公開検索API）を使っている。
OSRM同様APIキー不要で試せる一方、あくまで公開のコミュニティ運営サービスであり、
高頻度・大量な利用や商用の常用は利用ポリシー上想定されていない（目安として
1リクエスト/秒程度）。そのため自動補完（入力のたびに検索する方式）は行わず、
検索ボタン／Enterキーを押した時だけ1回叩く。日本国内の検索に絞るため
`countrycodes=jp`を指定している。

### お気に入り機能について

`/karte/favorites`（ヘッダーの「★ お気に入り」）。ログイン機能が無いMVPのため、
ホーム位置と同様、事務所全体で共有する1つのお気に入りリストとして実装している
（`Favorite`テーブル。カルテ1件につき高々1件）。

グルーピング（例:「今年の点検場所」）は別テーブル`FavoriteGroup`への多対多
（明示的な中間テーブル`FavoriteGroupItem`）とし、1件のお気に入りを複数グループへ
同時に所属させられるようにしている。お気に入り画面では、グループの作成・
絞り込みタブに加え、該当する場所を確認できる地図（`components/MapView.tsx`を再利用）と
調書（カルテ）の一覧テーブルの両方を1画面にまとめている。

カルテ詳細画面のヘッダーにある☆/★ボタン（`components/FavoriteToggleButton.tsx`）は
フォームを介さず、クリックで直接Server Actionを呼んで結果に応じて表示を更新する
（お気に入りは軽い操作のため、ページ遷移やフォーム送信を伴わせたくないため）。

地図上のマーカーを選択した時のポップアップ（`components/MapView.tsx`）にも同じ
切り替えを置いており、「地図でカルテを触ったその場でお気に入りに追加できる」
ようにしている（ホーム/現在地からの距離と同じ理由で、状態はrefで保持しポップアップを
開き直すたびに再描画する）。

### 編集履歴・閲覧履歴について

ヘッダーに性質の異なる2つの履歴ボタンを置いている。

- **編集履歴**（`/karte/history`）: カルテ・点検対象・点検記録の作成/更新/削除、
  Excel取込を対象にした簡易監査ログ（`AuditLog`テーブル、`lib/audit.ts`）。
  事務所全体で共有するサーバー側データのため、専用ページとして実装している。
  ログイン機能が無いため「誰が」は記録できず、「いつ・何を・どう変更したか」の
  短いサマリ文字列のみを保持する（詳細差分やロールバックは持たない）。
  ログの記録に失敗しても本来の保存処理自体は失敗させたくないため、
  `logAudit()`内で例外を握りつぶすようにしている。
- **閲覧履歴**（ヘッダーの「🕘 閲覧履歴」ドロップダウン）: 直近に開いたカルテ詳細画面。
  「誰が何を見たか」は個人の端末内だけの関心事であり事務所で共有すべきではないと
  考え、サーバーには一切保存せず、端末のlocalStorageだけで完結させている
  （`components/ViewHistoryButton.tsx`・`components/RecordViewHistory.tsx`）。
  この非対称性（一方はサーバー共有ページ、他方はクライアントローカルなドロップダウン）は
  意図的なもので、それぞれのデータの性質に合わせている。

### 処理中インジケータについて

検索・Excel取込・画像アップロード・保存等、時間のかかりうる操作で「処理中である」
ことが画面から常に分かるようにしている（指示書フィードバック: 何も表示されず
「システムが止まったのか」と思わせる状態を避ける）。

- **検索・画面遷移**: `app/karte/loading.tsx`（Next.js App Routerの規約に沿った
  Suspenseフォールバック）。検索条件を変えて再送信した際や、別のカルテへ
  遷移した際、DBへの再フェッチが終わるまで自動的にスピナー画面を表示する。
  `/karte`以下の全ルートに継承されるため、個別ページごとに用意する必要が無い。
- **Excel取込**: `components/ExcelImportForm.tsx`。アップロード進捗（%）→
  フェーズ単位の進捗（カルテ基本情報→点検対象1件ずつ→点検記録）を表示する
  （詳細は上記「Excel取込について」参照）。
- **写真アップロード**: `components/PhotoUploadForm.tsx`。`useActionState`の
  `isPending`でボタンを無効化し「アップロード中...」と表示する。
- **各種保存フォーム**: `components/SubmitButton.tsx`・`components/ConfirmSubmitButton.tsx`。
  `useFormStatus()`で自身が属する`<form>`の送信中状態を検知し、ボタンを無効化・
  スピナー表示に切り替える。カルテ・点検対象・点検記録の登録/編集フォーム全てで
  共通化している（`useFormStatus`は最も近い祖先`<form>`の状態しか読めないため、
  必ず`<form>`の内側に置く必要がある）。
- **お気に入りの切り替え**: `components/FavoriteToggleButton.tsx`。`useTransition`で
  楽観的に表示を切り替え、失敗時のみ元に戻す。

## スタック

Next.js（App Router）+ TypeScript + TailwindCSS + Prisma + PostgreSQL。Vercelへのデプロイを想定。

## セットアップ

### 1. 依存関係のインストール

```bash
npm install
```

### 2. データベースの用意

Vercel Postgres（Neon）を使うのが最も簡単（Vercelダッシュボード → Storage → Create Database → Postgres）。
ローカルのみで試す場合は Neon の無料枠を別途作成するか、Docker で代用できる。

```bash
docker run --name karte-db -e POSTGRES_PASSWORD=postgres -p 5432:5432 -d postgres:16
```

`.env.example` を `.env` にコピーし、`DATABASE_URL` を接続文字列に置き換える。

### 3. マイグレーションとサンプルデータ投入

```bash
npm run prisma:migrate   # テーブルを作成
npm run db:seed          # サンプルカルテ（架空データ）を投入
```

### 4. 開発サーバー起動

```bash
npm run dev
```

`http://localhost:3000` にアクセスするとカルテ一覧へリダイレクトされる。

## Vercelへのデプロイ

1. このリポジトリ（`webgis-mvp/`をルートとして）をVercelにインポート
2. Vercelダッシュボードで Postgres（Neon）を作成し、プロジェクトに接続すると
   `DATABASE_URL` が自動的に環境変数として設定される
3. デプロイ後、初回のみ `npx prisma migrate deploy` を実行してテーブルを作成する
   （Vercelのビルドコマンドに含めるか、ローカルから本番の`DATABASE_URL`に向けて実行する）
