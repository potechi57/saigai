# データバックアップ・復旧計画

本番実装に向けた優先事項の1つ「データバックアップ・復旧計画」として整備した内容と、
実際に障害・誤操作が発生した際の復旧手順をまとめる。

## 現状のバックアップ体制

対応方針: **追加費用なしでできる範囲で復旧可能期間を延ばす**（Neonの有料プランへの
アップグレードは行わない）。アップロード済み画像（点検写真・台帳画像、Vercel Blob）は
今回のバックアップ対象に含めていない（DBのURL参照が失われるリスクは低いと判断し、対象外）。

| 対象 | 手段 | 復旧可能期間 | 粒度 |
|---|---|---|---|
| DB（直近） | Neon Point-in-Time Restore（Freeプラン標準機能、追加設定不要） | 過去24時間 | 任意の時刻（分単位） |
| DB（長期） | GitHub Actions `.github/workflows/db-backup.yml` による毎日の`pg_dump`（Artifactsとして保存） | 過去30日（日次） | 1日1回時点のスナップショット |
| Vercel Blob（画像） | なし | — | — |

この2つを組み合わせることで、「昨日の朝の操作ミスに気づいた」ような直近のケースは
Neon側のPITRで、「1週間前に登録したデータが消えている」のような気づくのが遅れた
ケースはGitHub Actionsの日次ダンプで、それぞれ対応できる。

### GitHub Actions側の事前準備（未実施の場合、ワークフローはエラーで停止する）

リポジトリの **Settings > Secrets and variables > Actions** で、以下のSecretを設定する。

- `BACKUP_DATABASE_URL`: 本番DBの**プーリングなし（direct）接続文字列**
  - Neonダッシュボード → 対象プロジェクト → `production`ブランチ → Connect to your
    database → "Pooled connection"のチェックを**外した**状態のもの
  - ホスト名に`-pooler`が付いていないことを確認する（`pg_dump`はコネクションプーリング
    〔PgBouncer〕経由だと正常に動作しないことがあるため）

設定後は `Actions`タブ → `DB Backup`ワークフロー → `Run workflow`で手動実行し、
Artifactが正常に生成されることを一度確認しておくとよい。

## 復旧手順

### ケース1: 直近24時間以内の誤操作・データ破損（Neon PITR）

1. [Neonダッシュボード](https://console.neon.tech) → 対象プロジェクト → **Branches**
2. `production`ブランチの `...` メニュー → **Restore**
3. 戻したい時刻（分単位）を指定して実行
   - 不安な場合はまず「新しいブランチとして復元」し、内容を確認してから
     `production`に反映する方が安全（Neonの復元機能はブランチ作成としても使える）
4. 復元後、アプリ（Vercel）側は特に再設定不要（同じ接続文字列のまま中身だけ戻る）

### ケース2: 24時間より前の時点に戻す必要がある場合（GitHub Actionsのダンプから復元）

1. GitHubリポジトリの **Actions** タブ → **DB Backup** ワークフロー →
   戻したい日付に近い実行を選び、Artifact（`db-backup-<run id>`）をダウンロードして展開する
   （`db-backup.dump`が得られる）
2. 復元先を用意する。**本番へ直接上書きする前に、必ずNeonで新しいブランチを作成し、
   そちらに復元して内容を確認する**（Neonダッシュボード → Branches → Create branch、
   親は`production`で可。復元時にどうせ上書きされるので親ブランチの時点は問わない）
3. 作成したブランチの「プーリングなし」接続文字列を控え、`pg_restore`で復元する
   （ローカルにPostgreSQLクライアント一式が必要。`brew install postgresql` /
   Windowsは[EDBのインストーラー](https://www.postgresql.org/download/windows/)等）

   ```
   pg_restore --no-owner --no-privileges --clean --if-exists -d "<復元先の接続文字列>" db-backup.dump
   ```

4. 復元したブランチの内容をアプリ（開発環境等）から接続して確認する
5. 問題なければ、そのブランチを`production`に昇格させるか、同じ内容を
   `production`ブランチに対して同じ`pg_restore`コマンドで反映する
   （Neonダッシュボードの「Set as default」やブランチ操作で対応。手順3の接続文字列を
   本番のものに差し替えるだけでも同じ内容を反映できる）

### ケース3: Vercel Blob（画像ファイル）を誤って削除した場合

現状、復旧手段はない（バックアップ対象外のため）。運用でカバーする
（削除操作は慎重に行う、削除前に確認ダイアログを設ける等）。将来的に必要性が
高まった場合は、DBと同様にGitHub Actions等で定期的に一覧・URLをエクスポートする
仕組みを追加することを検討する。

## 体制・役割

- 現時点ではチーム規模が小さいため、担当者を限定せず「気づいた人が本ドキュメントの
  手順に従って対応する」運用とする。実際の障害対応を行った場合は、原因と対応内容を
  簡単にでも記録に残すことを推奨する（次回同種の障害が起きた際の参考にするため）。

## 既知の制限・今後の改善余地

- DB接続に使うロールが読み書き権限を持つ単一ロールのみ（セキュリティレビューで
  指摘済みの既知事項）。`BACKUP_DATABASE_URL`も同じロールを使っているため、
  将来的には読み取り専用ロールを別途作成し、バックアップ専用に使う方が望ましい
- 画像（Vercel Blob）のバックアップは今回スコープ外
- 復元訓練（実際に手順2を試してみること）は本ドキュメント作成時点では未実施。
  一度は実際に試しておくことを推奨する
